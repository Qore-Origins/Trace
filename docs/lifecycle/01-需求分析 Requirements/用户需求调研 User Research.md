## 1. 调研概述 Research Overview

### 1.1 调研背景 Research Background

本项目为**个人自用工具**（来源：个人生活需求），用户 = 开发者本人。调研对象即用户本身：长期多载体（笔记/Markdown 文档/聊天记录/任务 App）管理个人计划（学业、开发项目、生活）形成的真实痛点，已书面化于 `Future_Plan-20260825-桌面端计划管理软件`。

**诚实声明：** 未做外部用户抽样调研（样本=1，即本人）；本调研以"自我实践复盘 + 现代计划/笔记类工具的公开竞品对照"为主要方法，结论仅服务 v1.0 自用目标。若未来开源面向公众，须重新执行正式用户调研（见 §7 建议）。

### 1.2 调研目标 Research Objectives

| 序号 ID | 调研目标 Objective | 预期成果 Expected Outcome |

| 2 | 明确"计划"对象应有的最小能力集 | MVP 功能清单（存储/渲染/溯源查询三模块） |
| 3 | 对照现有工具验证"自研"必要性 | 竞品简析（Notion/滴答清单/Obsidian/印象笔记） |

## 3. 目标用户画像 User Personas

### 3.1 主要用户画像 Primary Personas

#### 画像1：个人计划管理者（开发者本人）

**基本信息 Basic Information:**

| 属性 Attribute | 信息 Information |
|--------------|----------------|
| 姓名 Name | HeYS-Snowe（虚拟化：调研对象即本人） |
| 常见名称/身份 | 学生、个人开发者（项目地图含学业、兴趣、比赛、AI 研究等多线） |
| 年龄 Age | 20 岁左右（在校生） |
| 职业 Occupation | 学生 + 全栈个人开发者 |
| 收入水平 Income | 学生（无工资收入记录） |
| 教育程度 Education | 大专/高职在读 |
| 技术水平 Tech Savviness | 高（全栈 + AI 代理协作熟练，有 `.Rules`/`.prompt` 规则体系） |

**用户描述 User Description:**

多线程生活的"计划密集型"用户：学业、多个开发项目（Qore 系/Loop/Lumina/Minecraft Mod/比赛项目）、AI 研究、日常生活的计划与任务交织在一起。计划载体分散且混用（各类笔记、Markdown 文档、聊天记录、任务 App），产生五类痛点（见 §6）。

**目标与需求 Goals & Needs:**

| 目标类型 Goal Type | 具体描述 Description |
|-----------------|-------------------|
| 核心目标 Primary Goal | 用单一应用统一承载全部个人计划，任何计划"有迹可循" |
| 次要目标 Secondary Goal | 计划排版规范、任务可追踪、编辑成本低（免 markdown 语法负担） |

**痛点与挑战 Pain Points & Challenges:**

1. 计划排版乱：不同计划格式五花八门，阅读/复盘成本高
2. 集成管理差：分散存储，无单一入口
3. 任务管理差：任务与计划脱节，无状态追踪
4. 溯源、查询困难：找不到某计划/任务的源头（检索无门）
5. 计划编辑难：直接编辑 markdown 心理门槛高，计划易过期

**使用场景 Usage Scenarios:**

学期计划制定（嵌套文件夹：学期→科目/项目→周计划）→ 周计划执行（任务勾选）→ 复盘（注释记录）→ 溯源（"这个任务从哪个计划来？"）

**技术偏好 Tech Preferences:**

本地优先、明文件（文件夹可拷贝、可用任何工具读取）；无网络依赖；偏好组件化、低学习成本交互；愿为"可溯源"付出结构化成本。

**引用语录 Quote:**

> "溯源、查询困难"——计划有迹可循，随时回到源头。

### 6.2 痛点详细分析 Detailed Pain Point Analysis

#### PP-001: 计划排版乱

**痛点描述 Description:**
不同计划用不同工具/格式书写（表格、纯文本、markdown、笔记模板），同一时刻风格不一，阅读/复盘需"重新翻译"。

**根本原因 Root Cause:**
"计划"没有统一的结构化载体——通用文档工具不区分"计划对象"，渲染完全依赖手写格式。

**当前影响 Current Impact:**

| 影响维度 Impact Dimension | 描述 Description |
|----------------------|----------------|
| 用户情绪 User Emotion | 烦躁（"又要整理格式"） |
| 时间成本 Time Cost | 每次阅读/复盘需适应格式 |
| 效率损失 Efficiency Loss | 计划利用率下降，格式整理挤占执行时间 |

**潜在解决方案 Potential Solutions:**

1. 计划单片组件：以 5 类组件定义计划内容结构（单选/多选/任务列表/任务详情/注释）
2. 组件即排版：渲染逻辑固定，用户不再关心格式
3. 模板化：预置"周计划/学期计划"等模板（远期 P2）

#### PP-002: 集成管理差

**痛点描述 Description:**
计划散落在笔记、文档、聊天记录三个以上载体，没有一处"全貌"，制定计划时需要跨工具搬运。

**根本原因 Root Cause:**
无计划专用的统一存储；"一处管理"缺位。

**当前影响 Current Impact:**

| 影响维度 Impact Dimension | 描述 Description |
|----------------------|----------------|
| 用户情绪 User Emotion | 失控感 |
| 时间成本 Time Cost | 检索/搬运时间 |
| 效率损失 Efficiency Loss | 计划遗漏、重复制定 |

**潜在解决方案 Potential Solutions:**

1. 计划库根目录 + 文件夹树：全部计划集中在单一根目录
2. 单一入口应用：打开即全貌
3. 明文件存储：迁移/备份简单，杜绝"工具锁定"

#### PP-003: 任务管理差

**痛点描述 Description:**
任务与计划脱节（任务写在别处），无状态（有无完成过靠记忆）。

**根本原因 Root Cause:**
通用工具将"任务"当普通文本，无状态机与归属。

**当前影响 Current Impact:**

| 影响维度 Impact Dimension | 描述 Description |
|----------------------|----------------|
| 用户情绪 User Emotion | 欠账感 |
| 时间成本 Time Cost | 反复确认完成状态 |
| 效率损失 Efficiency Loss | 任务漏做/重复做 |

**潜在解决方案 Potential Solutions:**

1. 任务列表/任务详情组件：计划内嵌任务、状态可追踪
2. 状态机：未开始 → 进行中 → 完成（展示层判定逾期）
3. 溯源反查："这个任务属于哪个计划"（配合 FR-009）

#### PP-004: 溯源、查询困难

**痛点描述 Description:**
历史计划、任务的来源无法找回：想查"当时为什么定这个目标/这周任务来自哪"，需要逐文档翻找，经常失败。**这是应用命名（溯源）的直接依据。**

**根本原因 Root Cause:**
计划内容无索引、无归属路径，存储载体（笔记/聊天）无计划语义的检索能力。

**当前影响 Current Impact:**

| 影响维度 Impact Dimension | 描述 Description |
|----------------------|----------------|
| 用户情绪 User Emotion | 挫败（"读过、写过但找不回"） |
| 时间成本 Time Cost | 翻找时间不可控 |
| 效率损失 Efficiency Loss | 经验无法复用，历史计划等于丢失 |

**潜在解决方案 Potential Solutions:**

1. 本地索引：对计划/任务/注释建立检索索引（名称 + 内容）
2. 来源回溯：命中项 → 所属计划路径一键定位
3. 检索范围设计：包含注释（经验沉淀）与任务（执行记忆）

#### PP-005: 计划编辑难

**痛点描述 Description:**
直接编辑 markdown/文档时，语法负担高、易出错、轻度修改也要面对整篇文本；"改一下就去写另外的载体"。

**根本原因 Root Cause:**
"渲染（阅读态）"与"编辑（写态）"分离的通用工具里，编辑成本被放大；markdown 语法是隐性门槛。

**当前影响 Current Impact:**

| 影响维度 Impact Dimension | 描述 Description |
|----------------------|----------------|
| 用户情绪 User Emotion | 拖延（改计划 = 负担） |
| 时间成本 Time Cost | 修改计划耗时 = 重写成本 |
| 效率损失 Efficiency Loss | 计划过期不更新，计划失去价值 |

**潜在解决方案 Potential Solutions:**

1. 组件内编辑：渲染即编辑——点中即改，免语法
2. 自定义渲染模块：替代"直接渲染 markdown"的初版设想（方案决策，2026-08-25）
3. 局部编辑：只修改目标组件，不面对整篇

## 7. 调研结论 Conclusions

### 7.1 关键发现 Key Findings

1. 需求真实性高：痛点由用户（=开发者）长期实践直接验证，样本可信度等同于"用户即产品负责人"，但**外部普适性未验证**（单用户）。
2. 自研必要性成立：竞品各有擅长（记笔记/任务清单/本地 markdown），但"计划语义（文件夹即计划 + 五类组件 + 溯源）"为空缺，通用工具均需组合使用。
3. 方向已在方案固化：存储模块（文件夹存储，可嵌套、拖拽）+ 页面渲染模块（自定义组件渲染）已定，本次补充**溯源查询**为第三模块补齐痛点闭环（本项目确认进 MVP）。
4. 数据语义是差异化根本：计划=文件夹 + 组件化内容，使"溯源"（路径 + 内容索引）天然成立。
