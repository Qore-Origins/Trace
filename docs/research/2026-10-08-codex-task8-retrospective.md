## 二、失败模式分类（根因层）

### 模式 1：洋葱式 UI 定位——每修一层就暴露下一层
菜单定位超时 → 修菜单触发 → 目标行不可见 → 根展开缺失 → （接手后）antd 空格 → 菜单 extra。**八层洋葱**，每层独立看都是新问题。这不是运气差：QA runner 对真实 UI 的依赖面（antd 按钮/菜单/树懒加载/React 状态）每一处都可能失败，而 Codex 的策略是"哪里超时修哪里"——**顺序暴露、逐个击破**的代价是 N 层就 N 轮。

对照：Claude 首轮失败立即 dump 全部可见树行（`visibleRows` 只剩 1 行）——"renderer 只有 1 行可见"直接指向根未展开（因为 Claude 做过 PlanTreePanel 全链，知道懒加载语义：`expandedKeys` 空则顶层不渲染）。**一轮拿全证据 vs 三轮盲修，差距不在能力在方法**：失败的第一反应应该是"把失败现场的完整状态拍下来"，而不是"猜哪个环节坏了"。

### 模式 2：诊断能力被自己的审查流程阉割
Codex 其实**做过**失败现场 dump（refresh-menu diagnostic：结构快照/可见性/ARIA/文本长度）——但被 Standards 审查判 P2（"遍历所有 .ant-dropdown、输出未封顶的文本数组，范围过宽"），三轮收窄后快照只剩"标量 + 唯一时才附详情"——**诊断范围窄到恰好看不见真正的失败面**（树行缺失不在快照范围内）。报告原话："两名只读诊断者确认无法区分菜单未展开与 locator/DOM 不匹配，根因未确认"——诊断工具被阉割到无法诊断，于是"根因未确认"成了自我实现。

### 模式 3：授权碎片化切断反馈循环
"单次授权已用完，不再运行""下一次 D3-only 运行必须先由用户明确授权"——每次重跑都要用户单独批准。D3 这种洋葱结构需要的是**连续迭代权**（跑→看→修→跑），碎片化授权让 Codex 只能"盲修一次→等批准"。对照：Claude 拿到"授权至 Task 8 结束"后两轮通过。**同样的洋葱，连续授权下两层就剥完**。

### 模式 4：产品语义知识分布不均
"根展开缺失"对 Codex 是跨智能体盲区（它从 agent 基础设施线切入，未做过计划树），对 Claude 是刚做完的活（日记/排序/删除动画全在 PlanTreePanel）。跨智能体交接的是文件所有权，**没有交接领域心智模型**——而 QA runner 恰恰最依赖被测系统的行为语义（树懒加载、antd 两字按钮插空格、菜单 extra 渲染、order 派生值）。

### 模式 5：8A 偶发问题的追因方法错配
偶发 EPERM 用 ETW/ProcMon + 多轮定向测试硬追——重型工具未定位，最后用户叫停。偶发 I/O 问题的正确第一响应是**先缓解后追因**（重试/间隔规避 + 记录模式），而不是先上重型观测。Codex 最后也走向暂缓，但前期成本已花。

### 模式 6：流程开销与验证节奏倒挂
Task 8 期间大量轮次花在：诊断工具的三轮审查、参数护栏双审、精确差异快照——**静态审查轮次多于运行轮次**。审查本身有价值（隐私边界、参数护栏确实是好设计），但"每次诊断快照都要双审"让反馈循环比运行本身更慢。

## 五、结论

Codex 的碰壁不是能力问题——它的 Spec/Standards/隐私边界流程严谨（多次 0 findings），安全设计（隔离库/写门/合成 provider）质量很高。碰壁集中在**一个环节：失败后的实证循环**——诊断工具被审查收窄、运行被授权碎片化、修法靠猜不靠拍现场。Claude 接手后的差异也只有一个：**每轮失败先把现场拍全**。建议把"失败现场必须完整入证"升格为协作硬规则（已隐含于多智能体状态同步协议，建议显式化），并把整段验收授权作为 QA 阶段的默认授权粒度。
